03

How it works, in one line

A founder types one intent. The backend wakes only the AI "departments" it needs, they work in parallel, review each other, and return one answer — which the UI shows calmly while everything is remembered for next time.

UI
Intent

You type a goal on the Command Surface.

→
BACKEND
Plan

The COO splits it into tasks; picks the cheapest capable model.

→
BACKEND
Work

Agents run in parallel & review each other.

→
UI
Answer

One synthesized answer + cost + reasoning.

→
BACKEND
Remember

Decisions & assets saved to memory.

04

Backend, explained simply

you build these

Each is an independent module in packages/. Build them in this order — each one makes the next possible.

Database (MongoDB)

Where everything lives: workspaces, projects, runs, memory. Flexible documents, no rigid schema fights.

packages/db · collections + repositories

Event Log

An append-only history of everything that happens. Memory, the timeline, and the decision log are all "views" of it.

packages/db · the source of truth

Model Router

One doorway to all AI models. Always picks the cheapest model that can do the job; swaps providers without touching other code.

packages/ai-providers

Memory Engine

Curated, searchable memory per project. Gets smarter over time — the real moat.

packages/memory + knowledge-graph

Agent Orchestrator

The "COO" that turns one intent into coordinated work and one answer. The brain.

packages/agents

Queue & Workers

Long jobs (big runs, video processing) run in the background with BullMQ — the UI never freezes.

packages/queue + services/worker
05

Frontend, explained simply

I build these

All in apps/web. The look is "Strata" — calm, dark, premium; not a busy dashboard.

Screens

Each screen lives in features/. The home is the Command Surface.

Design system

Reusable components + Strata tokens in shared/ui. One look, every screen.

Adaptive themes

Each project gets its own accent (FinTech, Health…) on one substrate.

Motion

Framer Motion + GSAP — premium, meaningful, never noisy.

State

Server data via React Query; global UI via Redux Toolkit. I set the patterns; you wire real data.

States & a11y

Loading, empty, error states + keyboard + reduced-motion, every screen.

Yes — screen & visual capture is covered

You asked if I have info on the screenshot/video capture idea. I do — it's the multimodal memory part of the architecture. Here's the plan in plain terms.

How "visual capture" works

FounderOS doesn't just store a screenshot — it understands it and remembers the meaning, so it can reuse your design and spot UX issues later.

1 · CAPTURE
Upload or grab

Drop a screenshot, a screen recording, or a design file. (UI: me)

2 · PROCESS
Worker + FFmpeg

Video is split into key frames/steps in the background. (Backend: you)

3 · SEE
Vision model

A vision model reads the image → layout, colors, spacing, friction points.

4 · REMEMBER
Into memory

The structured meaning (not just the file) is saved & linked in the graph.

5 · REUSE
Design DNA

Feeds your personal design language + UX/QA review later.

Lives in: packages/storage (files) · services/worker (FFmpeg + vision) · packages/memory (meaning) · later → Design DNA. Scheduled for Sprint 5.

## ★ Strategy change — 2026-10-02: projects first, FounderOS reshaped from evidence

The founder's decision: **don't finish FounderOS before building products.** Build the ten
products directly, each in its own standalone folder, with a coding agent plus Gemini and
free keys. Evolve FounderOS **in parallel**, shaped by what the real builds teach.

| Before | Now |
|---|---|
| FounderOS steps 2–8 first, then products through FounderOS | Products start now in `projects/<slug>/`; FounderOS is not on their critical path |
| Foundation template designed up front | Template **extracted from LedgerWeave** after it passes its gates — designed from a real product |
| Build Pack generated by FounderOS | v0 already exists: each project's `CLAUDE.md` + `details/prompts.md` |
| Research stage built into FounderOS | Crawler used standalone; integrated only after its **7-run gate** opens (`Product-Research-Engine/gate/`) |
| — | Each project keeps `details/founderos-notes.md`; FounderOS work is chosen from those notes |

**How a finished product enters FounderOS:** Projects → *Built projects* → *Add to
workspace* → *Run eject check* (shipped in step 1). The receipt proves it stands alone.

**What stays true:** the doctrine, the eject invariants, receipts, free-first, one
product at a time to its gates, LedgerWeave first.

## 0 · The honest starting point

**What FounderOS does well today:** *thinking*. Minimum-set activation, the department
debate, CEO synthesis, receipts, memory, cost governance, the Freelance Studio. That is the
top half of the chain, and it works.

**What it cannot do yet:** *build*. FounderOS does not write files into a project, run
`npm install` / `typecheck` / `test` / `build`, read the errors, and fix them. That
write → run → read-errors → fix loop is the entire capability that makes a coding tool feel
like a coding tool. **Without it, "end-to-end" stops at a plan.**

So this plan adds one new engine — the **Build Engine** — plus a **Design Studio**, and puts
everything else we already have to work around them.

> Doctrine note: we plan to a *capability bar* (a working, tested, ejectable product),
> never to a comparison with other tools. No product copy or doc will claim parity with
> anyone.

## 1 · The pipeline — every product goes through these eight stages

| # | Stage | What happens | Built? | Output (saved in `projects/<name>/details/`) |
|---|---|---|---|---|
| 1 | **Research** | Product-Research-Engine L1–L5 on the 3 reference products + Prompt A | ✅ exists (standalone) | `research.md`, reference matrix |
| 2 | **Debate** | The council challenges scope; the CEO cuts to one proof workflow | ✅ exists | `blueprint.md`, `debate.json`, `decisions.md` |
| 3 | **Design** | Screens for the proof workflow, on the product's own design tokens | 🟡 new — Design Studio | `design/*.html`, `DESIGN.md` |
| 4 | **Scaffold** | Copy the shared foundation template into `projects/<name>/` | 🟡 new — Track A | `project.json`, app skeleton |
| 5 | **Build** | Task-by-task code generation with the write→run→fix loop | ❌ new — Build Engine | source code, commits |
| 6 | **Verify** | Release gates: typecheck · tests · build · 5 states · eject check | 🟡 partial (eject planned) | `gates.json` (receipts) |
| 7 | **Package** | README, demo script, evidence bundle, eject zip | 🟡 new | `release/` |
| 8 | **Sell** | Gumroad listing + Contra service draft + proof pack | ✅ exists (Freelance Studio) | listing, case study |

Each stage has a **human approval gate**. You approve the blueprint before design,
the design before build, and the gates before package. Nothing moves forward silently.

## 2 · The Build Engine — two paths, in order

### Path 1 — "Build Pack" (usable this week, no new risk)

FounderOS does stages 1–4 and then **writes a Build Pack**: an ordered task list where each
task has its goal, the files it touches, acceptance checks, and the exact prompt.

A coding agent you already have executes it inside `projects/<name>/`:

- **Claude Code / Cowork** — what you use today.
- **Gemini CLI** — runs on your Google account.
- Any other CLI coding agent you prefer.

FounderOS then **runs the gates** (stage 6) and shows the receipts. It never has to trust
the coding agent's own claim that the work is "done".

**Why this first:** it is honest, it ships product #1 now, and the Build Pack format
becomes the exact input the native engine consumes later. Nothing gets thrown away.

### Path 2 — Native Build Engine (after product #1 ships)

FounderOS runs the loop itself through the local **project runner** (Track A Stage 2 —
long-lived processes must never run inside a Next.js route):

```
task → plan edit → write files (confined to projects/<name>/) → run check
     → read errors → fix → re-run → pass → commit → next task
```

| Concern | Rule |
|---|---|
| **Tools** | `read_file`, `write_file`, `list_dir`, `run_command` — nothing else |
| **Path confinement** | every path resolved and checked inside `projects/<name>/`; `..` rejected |
| **Command allowlist** | `npm install`, `npm run typecheck`, `npm test`, `npm run build`, `npm run lint` only; no shell interpolation of model output |
| **Budget** | max fix-iterations per task (e.g. 5), per-task token cap, per-run `RUN_BUDGET_USD`; on exhaustion it **stops and reports**, never loops |
| **Secrets** | no env values in prompts or logs; the project's `.env` is never read by the model |
| **Receipts** | every task logs its model, cost, files changed, commands run and exit codes |
| **Streaming** | progress over SSE, same pattern as `runs/stream` |

## 3 · The Design Studio (the "Stitch-like" stage)

**Goal:** you describe a screen, see it rendered, iterate, and approve it — then the
approved design becomes the input to the build.

- **Generation:** Gemini produces HTML + Tailwind for each screen of the proof workflow,
  constrained to that product's tokens (colour, type, spacing, radius).
- **Preview:** rendered in a sandboxed iframe inside FounderOS, with desktop/mobile toggle.
- **Five states per screen** are generated and reviewed: loading · empty · error ·
  success · degraded. A screen without all five doesn't pass.
- **Handoff:** approved screens + a `DESIGN.md` (tokens, components, rules) go to the Build
  Pack, so the coding stage builds *to* the design instead of re-inventing it.
- **Google Stitch:** it's a separate Google Labs tool. Public write-ups say it exports
  HTML/Tailwind and a `DESIGN.md`, and mention an MCP bridge. Use it as an **optional
  import**: design in Stitch, drop the export into `details/design/`. **Verify the
  export/MCP details when wiring — I have not tested them.**

## 4 · Models — who does what

| Job | Model | Why |
|---|---|---|
| Debate + critiques | free tiers (Groq, OpenRouter `:free`, Gemini Flash) | short, reactive, high-volume |
| CEO synthesis + blueprint | **Gemini Pro** (your key) | best reasoning seat available to you |
| Design generation | **Gemini Pro** | strong at HTML/Tailwind layout |
| Code generation + fixing | **Gemini Pro**, with **Grok** as the second opinion/fallback | long context, code-heavy |
| Embeddings / recall | free tier | cheap, frequent |

**Wiring Grok is one line.** xAI's API is OpenAI-compatible at `https://api.x.ai/v1`, so it
registers through the existing `OpenAICompatibleProvider` — no new adapter file. Credit
programs vary by account, so check your console before relying on them.

**Check your Google key first.** A **Google AI Pro subscription** (the consumer plan in the
Gemini app) is **not the same thing** as **Gemini API quota**. FounderOS needs a key from
`aistudio.google.com/apikey` with a free tier or billing attached. Check which one you have
before we plan capacity around it.

## 5 · The shared foundation (the plan's "reuse" promise)

The ten products share auth, tenants, roles, jobs, approvals, receipts, audit log, and the
design-token system. That becomes a **scaffold template** — `templates/foundation/`.
FounderOS **copies** it into each new project; it is **never linked**. Copying is what
keeps every product ejectable. If a template fix needs to reach existing products, it goes
in as a normal, reviewed change inside that project, not through a shared import.

Shapes needed across the ten:

- **Web** (Next.js + API + Postgres/Mongo): LumaPath, WardWeave, LedgerWeave, SourceWeave, FleetLens, ProofGate
- **Web + voice**: VoxRelay
- **Mobile (Expo)**: VaultRelay, IntentCart, MealMesh

So: one **web** template first, and a **mobile** template when product #4 starts.

## 8 · Honest limits

- The native Build Engine executes code on **your machine**. It must stay confined and
  allow-listed. It is not a remote sandbox and must never be exposed to other users until
  it runs in a real one.
- Generated code is a **draft until the gates pass**. FounderOS reports gate results; it
  never reports "done" on the model's say-so.
- Regulated domains (LumaPath, WardWeave, VaultRelay) ship as **bounded demos with
  simulators** that are clearly labelled. No clinical, banking or real-funds production
  claims.
- Free-tier limits and credit programs change. Nothing here depends on a specific quota
  number.

## 9 · FounderOS Workers — our own always-on company (added 2026-10-01)

**The outcome bar:** the company keeps working when the founder closes the laptop. A
department is no longer a one-shot prompt inside a run; it is a **standing Worker** that
wakes on a schedule or an event, does a bounded job inside one project, and leaves receipts.
We design to this bar ourselves — no parity claims with anyone (Doctrine).

> *A worker is a contract, not a personality.* (Roadmap principle, adopted as law here.)

### 9.1 · What a Worker is

| Part | Rule |
|---|---|
| **Contract** | role (PM · Architect · Design · QA · Research · Marketing · CEO), allowed tools, allowed project(s), budget per wake, max steps — stored as data, versioned, human-approved |
| **Sandbox** | `projects/<slug>/` only, through the same confinement as the Build Engine (`resolveInside`, command allowlist, no symlinks). Shipped foundation: Track A Stage 1. |
| **Memory** | the project's memory + the Worker's own log of past wakes (recall before re-deriving, §12) |
| **Triggers** | schedule (cron) · event (gate failed, new client note, listing went live) · manual |
| **Connectors** | only what the contract lists, via MCP/HTTP seams; credentials stay in env, never in prompts |
| **Approvals** | anything outward-facing or irreversible — publishing, emailing a client, spending, deleting — **stops and asks**. Workers draft; the founder ships. |
| **Receipts** | every wake logs model, cost, files touched, commands + exit codes, dissent — same shape as runs |
| **Kill switch** | pause one Worker or all; an exhausted budget pauses and reports, never retries forever |

### 9.2 · First Workers (each one useful on day one)

1. **QA Worker** — nightly: run the gates on every owned project, post a receipt, open an
   issue note on regressions.
2. **Research Worker** — morning: refresh the reference matrix for the active product
   (Product-Research-Engine) and file a cited diff into project memory.
3. **Marketing Worker** — after a project passes its gates: draft the Gumroad/Contra
   listing and proof post (Freelance Studio), awaiting approval.
4. **CEO Worker** — weekly: read every Worker's receipts and write the founder one decision
   memo, naming disagreements explicitly.

### 9.3 · Engines and cost

Free-first, unchanged: Workers route through `ModelRouter` — Gemini / Groq / OpenRouter free
tiers, Grok via `OpenAICompatibleProvider`, Echo as the floor. A frontier paid model can be
added later with **one registry line** when a key exists; nothing in the Worker design
depends on one. Idle Workers cost $0.

### 9.4 · Where it sits in the build order

Workers need three things already in this plan: the **sandbox** (step 1 ✅), the **gate
runner** (step 3) and the **project runner** (step 7, which owns long-lived processes and
schedules). So Workers land as **step 7½**, after the runner and before the native Build
Engine — the QA Worker first, because it only *reads and runs gates*, the safest possible
first job.

4. **typecheck / tests?** **Not run.** This is a plan; no code changed.
5. **Docs?** This plan, plus the dev-log and PROGRESS entries.
6. **Placeholders / secrets?** None.
